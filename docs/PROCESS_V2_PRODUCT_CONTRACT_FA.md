# قرارداد محصول و معماری فرآیندهای V2

این سند مرجع رفتار مورد انتظار «الگوهای فرآیند»، «اجرای فرآیند» و «فعالیت‌های فرآیندی» در همه سازمان‌ها و همه ماژول‌ها است.

## مدل مفهومی

«الگوی فرآیند» تعریف قابل استفاده مجدد فرآیند است. هر الگو شامل یک یا چند ردیف و مرحله است. هر مرحله می‌تواند مسئول، زمان‌بندی، وابستگی، دستورالعمل، اتوماسیون، فیلدهای اختصاصی فعالیت و وضعیت‌های اختصاصی فعالیت داشته باشد. برای هر الگو نیز می‌توان فعال‌کننده خودکار تعریف کرد.

وقتی الگو روی رکوردی از یک ماژول اجرا یا کپی می‌شود، یک نمونه مستقل و per-org از آن فرآیند شکل می‌گیرد. کاربر می‌تواند همه مرحله‌ها را یک‌جا ارجاع دهد، یک مرحله را جداگانه اجرا کند، پیش از ایجاد فعالیت تنظیمات پیش‌نویس را تغییر دهد، یا مرحله/ردیف/فرآیند تازه‌ای بسازد و از موارد قبلی کپی بگیرد.

## وضعیت‌های معتبر نمایش

رابط کاربری باید هر چهار حالت زیر را بدون ابهام پشتیبانی کند:

1. فقط پیش‌نویس: هنوز هیچ فعالیت واقعی ساخته نشده است.
2. فقط اجرای واقعی: همه پیش‌نویس‌های متناظر به فعالیت تبدیل شده‌اند.
3. ترکیبی: بخشی از مرحله‌ها فعالیت واقعی و بخشی هنوز پیش‌نویس‌اند.
4. چند فرآیند مستقل: یک رکورد می‌تواند هم‌زمان چند اجرای متفاوت یا چند گروه پیش‌نویس داشته باشد.

نبودن داده فقط پس از پاسخ موفق و قطعی سرور مجاز است. خطای شبکه، timeout، پاسخ قدیمی یا شکست یکی از queryها نباید باعث تبدیل محتوای موجود به صفحه خالی شود.

## قواعد تغییر وضعیت داده

- افزودن فرآیند، ردیف یا مرحله ابتدا به‌شکل optimistic نمایش داده می‌شود، اما موفقیت فقط پس از تأیید واقعی سرور اعلام می‌شود.
- اگر ذخیره تأیید نشد، UI باید به وضعیت قبلی rollback کند و پیام فارسی روشن نشان دهد؛ خطا نباید فقط در console ثبت شود.
- پس از تبدیل موفق یک پیش‌نویس به فعالیت، پیش‌نویس متناظر باید حذف و فعالیت واقعی در همان جای منطقی نمایش داده شود. حذف کل گروه فقط زمانی مجاز است که همه پیش‌نویس‌های آن گروه تبدیل شده باشند.
- ایجاد فعالیت یا اجرای جدید باید cache و snapshot همان رکورد را invalidate کند و نتیجه جدید بدون refresh دستی دیده شود.
- پاسخ قدیمی یک درخواست نباید پاسخ جدیدتر را overwrite کند.
- حذف، copy و جابه‌جایی باید هویت پایدار مرحله، `process_run`، ردیف و node را حفظ کند؛ تطبیق صرفاً بر اساس عنوان یا ترتیب کافی نیست.

## فیلدها و وضعیت‌های اختصاصی فعالیت

- تعریف فیلدها و وضعیت‌های اختصاصی هنگام ایجاد فعالیت در snapshot همان فعالیت نگهداری می‌شود تا تغییرات بعدی الگو رفتار فعالیت‌های قبلی را ناخواسته عوض نکند.
- مودال فعالیت V2 از هر مسیر ورود، از جمله ماژول فعالیت‌ها، اعلان، داشبورد و کارت فرآیند، باید رکورد canonical فعالیت را بخواند؛ داده خلاصه کارت برای بازکردن مودال کافی نیست.
- برای داده‌های قدیمی، context مرحله اجرای فرآیند و سپس مرحله الگو fallback معتبر هستند.
- مقدار فیلدهای اختصاصی باید به‌صورت merge اتمیک ذخیره شود تا ذخیره هم‌زمان دو فیلد باعث از دست رفتن مقدار قبلی یا سایر metadataها نشود.
- تغییرات استاندارد، فیلدهای مرتبط و وضعیت‌ها باید با RLS سازمانی و تأیید وجود رکورد ذخیره شوند. پاسخ موفق بدون ردیف تغییرکرده، موفقیت محسوب نمی‌شود.
- تغییر وضعیت باید ابتدا قواعد اجباری، قفل رکورد و دسترسی را بررسی کند و سپس ارتباط مرحله اجرا، وابستگی‌ها، زمان‌بندی و اتوماسیون را حفظ کند.

## رکوردهای مرتبط و مرز سازمان

- همه runها، stageها، taskها، linkها، cacheها و subscriptionها per-org هستند و در نبود `current_org_id()` باید fail-closed باشند.
- ارتباط یک فرآیند با چند ماژول از طریق linkهای صریح و snapshot ارتباط‌ها نگهداری می‌شود؛ primary record تنها مرجع نمایش نیست.
- copy یا append باید linkهای معتبر رکورد جاری را حفظ کند و هیچ UUID خامی در UI نشان ندهد.

## قرارداد بارگذاری و کارایی

- نماهای کامل، فشرده و ستونی از runtime مشترک و یک سیاست یکسان cache/invalidation استفاده می‌کنند.
- queryهای run، stage و task باید batch، محدود به ستون‌های لازم و قابل استفاده توسط index باشند.
- داده‌های مرجع مانند الگوها و مسئولان باید cache per-org و request deduplication داشته باشند.
- بارگذاری context تکمیلی مانند جایگزینی متغیرها نباید نمایش کارت‌های موجود را تا چند ثانیه مسدود کند.
- Realtime باید server-side filter داشته باشد و تغییر محلی معتبر را بلافاصله patch کند؛ refresh پس‌زمینه نقش تأیید و reconcile دارد.
- هنگام شکست بخشی از بارگذاری، داده معتبر قبلی حفظ و خطای قابل retry نمایش داده می‌شود.

## معیار پذیرش پایه

- افزودن یک الگو به رکورد دارای دو فرآیند، بلافاصله فرآیند سوم را نشان می‌دهد و پس از reload هر سه باقی می‌مانند.
- تبدیل یک مرحله پیش‌نویس، یک فعالیت واقعی ایجاد می‌کند و همان پیش‌نویس دیگر دیده نمی‌شود؛ سایر پیش‌نویس‌ها دست‌نخورده می‌مانند.
- بازکردن همان فعالیت از کارت فرآیند و ماژول فعالیت‌ها، فیلدها و وضعیت‌های اختصاصی یکسانی نشان می‌دهد.
- تغییر سریع چند فیلد اختصاصی هیچ مقداری را حذف نمی‌کند و خطای ذخیره موفقیت کاذب نمی‌سازد.
- پاسخ دیرتر یک request قدیمی باعث خالی‌شدن یا برگشت UI به snapshot قبلی نمی‌شود.
- نماهای کامل، فشرده و ستونی برای یک رکورد، مجموعه فرآیند و وضعیت یکسانی نمایش می‌دهند.
