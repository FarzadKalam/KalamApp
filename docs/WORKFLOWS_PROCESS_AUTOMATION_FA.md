# راهنمای گردش کارها و اتوماسیون فرآیند

**وضعیت:** مبنای طراحی و اجرای فاز بعدی  
**آخرین به‌روزرسانی:** 2026-03-31

این سند مرجع تصمیم‌گیری برای دو لایه‌ی متفاوت ولی هماهنگ در سیستم است:

1. `Workflow` عمومی روی رکوردها
2. `Process Automation` برای رفتارهای داخل اجرای فرآیند

هدف این سند این است که:

- از شلوغ شدن بیش از حد `workflow` فعلی جلوگیری کند
- اتوماسیون‌های مرحله‌ای و زمان‌محور را به‌صورت عمومی و قابل استفاده برای هر کسب‌وکار تعریف کند
- با ساختار فعلی پروژه، `process_templates` و `ProductionStagesField` همسو بماند

---

## 1) جمع‌بندی تصمیم اصلی

پیشنهاد نهایی این است:

- `Workflow` فعلی حفظ شود و برای اتوماسیون عمومی رکوردها استفاده شود.
- یک لایه‌ی جدید به نام `Process Automation` اضافه شود.
- ظاهر این لایه تا جای ممکن شبیه builder فعلی گردش کارها باشد.
- actionها و بخشی از helperهای `workflow` فعلی reuse شوند.
- اما trigger و context آن process-aware باشد.

این تفکیک مهم است چون مثال‌های واقعی کسب‌وکار بیشتر از جنس این رویدادها هستند:

- وقتی یک فعالیت از نوع خاص شروع شد
- وقتی یک فعالیت کامل شد
- وقتی چند ساعت تا موعد یک فعالیت مانده بود
- وقتی چند ساعت از موعد یک فعالیت گذشت
- وقتی باید به مسئول مرحله‌ی دیگری در همان فرآیند پیام داده شود

این‌ها با `record workflow` ساده قابل پیاده‌سازی هستند، اما به‌مرور شکننده و سخت‌فهم می‌شوند.

## 2) مرز بین Workflow و Process Automation

### 2.1) Workflow عمومی

برای این دسته از سناریوها مناسب است:

- وقتی رکورد جدید ایجاد شد
- وقتی رکورد ایجاد یا به‌روزرسانی شد
- وقتی شرایط فیلدهای رکورد برقرار شد
- ارسال پیامک
- ثبت یادداشت
- به‌روزرسانی رکورد
- ایجاد رکورد مرتبط
- کپی الگوی فرآیند
- اجرای خودکار فرآیند

### 2.2) Process Automation

برای این دسته از سناریوها مناسب است:

- وقتی task با نوع خاص وارد وضعیت خاص شد
- وقتی task تکمیل شد
- وقتی task اول یا آخر فرآیند بود
- وقتی باید به مسئول task دیگری در همان process پیام داده شود
- وقتی N ساعت قبل یا بعد از زمان task کاری انجام شود
- وقتی فرآیند روی رکوردی از یک ماژول خاص اجرا شده و باید به فیلدهای آن رکورد یا relationهایش دسترسی داشته باشیم

## 3) مدل مفهومی پیشنهادی

هر `Process Automation Rule` پنج بخش اصلی داشته باشد:

1. `Scope`
2. `Trigger`
3. `Conditions`
4. `Target Selector`
5. `Actions`

### 3.1) Scope

مشخص می‌کند rule برای چه چیزی تعریف شده است:

- کدام `process template`
- روی processهای کدام `target module`
- در صورت نیاز، روی کدام stage یا task type

### 3.2) Trigger

Triggerهای پیشنهادی فاز اول:

- `task_created`
- `task_status_changed`
- `task_started`
- `task_completed`
- `task_due_in`
- `task_overdue_by`
- `process_started`
- `process_completed`

نکته:

- triggerهای `task_due_in` و `task_overdue_by` باید scheduled باشند، نه scan دائمی کل رکوردها

### 3.3) Conditions

Conditionها باید از سه context اصلی پشتیبانی کنند:

- `Task Fields`
- `Process Fields`
- `Source Record Fields`

برای `Source Record Fields` باید این موارد در دسترس باشند:

- فیلدهای خود ماژول مبدا
- relationهای یک‌سطحی همان ماژول
- assignee
- tags

این منطق باید از `module_id` الگوی فرآیند تغذیه شود تا field list درست و context-aware ساخته شود.

### 3.4) Target Selector

این بخش از action جدا باشد و مشخص کند پیام یا اثر action روی چه کسی/چه چیزی اعمال می‌شود:

- مسئول همین task
- مسئول task از نوع X در همین process
- ایجادکننده رکورد مبدا
- مسئول رکورد مبدا
- مشتری یا مخاطب مرتبط
- کاربر یا نقش مشخص

### 3.5) Actions

actionهای پیشنهادی فاز اول:

- ارسال اعلان
- ارسال پیامک
- ثبت یادداشت
- به‌روزرسانی رکورد مبدا
- به‌روزرسانی رکورد مرتبط

actionهای پیشنهادی فاز دوم:

- ایجاد task جدید
- تغییر مسئول task
- block/unblock task
- complete/cancel task
- webhook

## 4) مثال‌های عمومی که این مدل باید پوشش دهد

این سناریوها باید بدون کدنویسی مستقیم و با builder قابل ساخت باشند:

- اگر فعالیت از نوع `تماس ورودی` ثبت شد، برای مشتری مرتبط پیام ارسال شود.
- وقتی task از نوع `طراحی` به وضعیت `در حال انجام` رفت، به مسئول task از نوع `چاپ` در همان process پیام داده شود.
- وقتی activity از نوع `طراحی` تکمیل شد، به بازاریاب و ایجادکننده‌ی پروژه پیام برود.
- وقتی task از نوع `نصب چاپ` تکمیل شد، به مسئول تبلیغات محیطی پیام داده شود.
- وقتی task خاصی تکمیل شد، وضعیت رکورد مرتبط در ماژول دیگر به مقدار جدید تغییر کند.
- وقتی دو ساعت تا زمان activity از نوع `جلسه` مانده بود، به مسئول آن پیام داده شود.
- وقتی چند ساعت از زمان activity گذشت، به مسئول آن هشدار داده شود.
- وقتی برای فاکتور حقوقی فرآیند خاصی اجرا شد، در مراحل پایانی به مسئول مالی اعلان ارسال شود.

## 5) پیشنهاد UI

### 5.1) ساختار کلی

بهتر است یک بخش مستقل کنار workflowهای فعلی اضافه شود:

- `اتوماسیون فرآیند`

ظاهر آن تا حد ممکن شبیه builder فعلی گردش کارها باشد:

- Trigger
- Conditions
- Actions

اما contextهای مخصوص فرآیند را هم داشته باشد:

- این task
- همین فرآیند
- رکورد مبدا فرآیند
- رکوردهای مرتبط رکورد مبدا
- taskهای دیگر همین فرآیند

### 5.2) نوع rule

برای جلوگیری از شلوغی فرم، ruleها در UI به سه گروه تقسیم شوند:

- `Task Event`
- `Task Time`
- `Process Event`

این تصمیم UI را ساده‌تر و قابل فهم‌تر می‌کند.

### 5.3) پیشنهاد برای stage-level automation

برای اتوماسیون‌های مربوط به یک stage خاص، rule باید بتواند stage یا task type را به‌عنوان context پیش‌فرض بگیرد.

مثال:

- `وقتی این stage کامل شد`
- `وقتی task_type این stage = طراحی بود`

## 5.4) وضعیت MVP پیاده‌سازی‌شده

در وضعیت فعلی کد، برای اینکه با حداقل تغییر و بیشترین reuse جلو برویم، MVP اولیه به این شکل پیاده شده است:

- اتوماسیون هر مرحله داخل `metadata` همان stage ذخیره می‌شود.
- محل نمایش و ورود آن در ماژول `process_templates` و در همان بلاک `مراحل الگو` است.
- این بخش بالای نوار `مراحل پیش‌نویس فرآیند` نمایش داده می‌شود تا کاربر اتوماسیون را جزو طراحی الگو ببیند، نه یک تنظیم پنهان و جدا.
- برای هر مرحله، دکمه‌ی جداگانه‌ی `افزودن/مدیریت اتوماسیون` وجود دارد.
- ویرایش stage و automation در همان modal `افزودن/ویرایش مرحله پیش‌نویس` انجام می‌شود.
- این modal به دو tab تقسیم می‌شود:
  - `مشخصات مرحله`
  - `اتوماسیون`
- به این شکل، entry point یکی می‌ماند ولی UI هنوز قابل‌فهم و قابل‌گسترش می‌ماند.

### رفتار اجرایی MVP فعلی

- هنگام ساخت task از روی stage، ruleهای همان stage داخل `tasks.recurrence_info.process_automation_rules` snapshot می‌شوند.
- بنابراین چه فرآیند از روی `الگوی فرآیند` کپی شود و چه با actionهای `copy_process_template` یا `execute_process` اجرا شود، ruleها همراه همان task منتقل می‌شوند.
- اجرای rule فعلی بر پایه‌ی `تغییر وضعیت task` است.
- action فعلی MVP یک `یادداشت روی رکورد مرتبط` است که به کاربر یا تیم هدف `mention` می‌دهد.

### trigger/action های پشتیبانی‌شده در MVP فعلی

- trigger:
  - `وقتی وضعیت فعالیت به مقدار X رسید`
- target:
  - مسئول همین فعالیت
  - مسئول مرحله بعد
  - مسئول فعالیتی از نوع مشخص در همان فرآیند
  - کاربر مشخص
  - تیم مشخص
- action:
  - ثبت یادداشت روی رکورد مرتبط با mention

### چیزی که فعلا عمدا deferred شده

- condition builder کامل شبیه workflow عمومی
- actionهای چندگانه
- ruleهای زمان‌محور
- log اجرایی مستقل برای هر rule
- موجودیت DB جدا مثل `process_automation_rules`

این‌ها deferred شده‌اند تا اول مسیر stage metadata و task runtime در عمل پایدار شود.

## 6) طراحی داده و منطق اجرا

### 6.1) پیشنهاد موجودیت جدید

پیشنهاد می‌شود موجودیتی شبیه این تعریف شود:

- `process_automation_rules`

فیلدهای حداقلی:

- `id`
- `org_id`
- `name`
- `is_active`
- `template_id`
- `module_id`
- `rule_type`
- `trigger_type`
- `trigger_config`
- `conditions_all`
- `conditions_any`
- `target_selector`
- `actions`
- `last_run_at`
- `created_at`
- `updated_at`

### 6.2) ذخیره‌ی stage binding

اگر rule برای یک stage خاص تعریف شود، یکی از این دو راه بهتر است:

1. `stage_sort_order` یا `stage_key` جداگانه ذخیره شود
2. یا داخل `trigger_config` و `target_selector` نگه‌داری شود

پیشنهاد بهتر:

- اگر در آینده stageها rename شوند، rule نباید به label فارسی وابسته باشد
- پس باید روی یک identifier پایدار تکیه کنیم

### 6.3) درباره‌ی task type

چون `task_type` داینامیک است:

- rule نباید label را ذخیره کند
- باید `value` پایدار option را ذخیره کند

اگر بعدا نام نمایشی تغییر کند، rule نباید بشکند.

### 6.4) درباره‌ی first / last stage

تشخیص `اولین` و `آخرین` stage نباید فقط بر اساس ترتیب نمایشی UI باشد.

حداقل در فاز اول:

- `sort_order` مبنا باشد

در فاز بعد:

- می‌توان `is_entry_point`
- و `is_final_step`
را هم اضافه کرد

## 7) پیشنهاد برای اجراهای زمان‌محور

برای ruleهای زمان‌محور مثل:

- 2 ساعت قبل از task
- 3 ساعت بعد از task

پیشنهاد این است:

- به‌جای scan مداوم روی همه‌ی taskها
- برای هر رخداد لازم یک job زمان‌دار ثبت شود

مدل بهتر:

- event ruleها لحظه‌ای اجرا شوند
- time ruleها روی queue / scheduled jobs اجرا شوند

مزایا:

- مصرف کمتر
- دقت بالاتر
- کنترل بهتر روی retry
- جلوگیری از full scan روی جدول‌ها

## 8) وضعیت پیشنهادی برای ماژول الگوهای فرآیند

### 8.1) فیلدهایی که دیگر لازم نیستند

با توجه به مسیر جدید، این فیلدها در `process_templates` دیگر value اصلی ندارند و بهتر است حذف یا deprecated شوند:

- `process_kind`
- `auto_copy_mode`
- `source_bom_id`

دلیل:

- `module_id` همان نقش تعیین scope را بازی می‌کند
- کپی خودکار بهتر است از طریق workflow یا process automation rule انجام شود
- ارجاع به BOM برای الگوی عمومی فرآیند، domain-specific و محدودکننده است

### 8.2) فیلدهایی که باید بمانند

- `name`
- `module_id`
- `is_active`
- `description`
- `template_stages_preview`

### 8.3) نکته‌ی migration

در حذف این سه فیلد باید دقت شود:

- اگر داده‌ی قبلی دارید، ابتدا UI و runtime از آن‌ها جدا شوند
- بعد migration حذف یا deprecated انجام شود
- indexها و constraintهای مربوط هم جمع شوند

## 9) بررسی بخش مراحل الگو

در وضعیت فعلی، `template_stages_preview` هسته‌ی اصلی تعریف stageهاست و همین مسیر برای حداقل تغییر مناسب است.

Stage draft فعلی این داده‌ها را نگه می‌دارد:

- نام مرحله
- ترتیب
- نوع فعالیت
- توضیحات
- مسئول پیش‌فرض
- وزن
- دستمزد
- زمان نسبی اجرا

این برای تعریف stage خوب است، اما هنوز برای automation کافی نیست.

### 9.1) جمع‌بندی

بخش مراحل الگو باید در فاز بعدی همچنان دو مسئولیت داشته باشد:

1. تعریف stage metadata
2. نمایش summary از ruleهای مرتبط

اما builder کامل ruleها بهتر است از خود stage form جدا بماند.

## 10) درباره‌ی مودال «افزودن مرحله پیش‌نویس فرآیند»

### 10.1) وضعیت فعلی

این مودال الان برای stage metadata مناسب است، اما برای rule builder کامل کوچک است.

همچنین از نظر visual tone با بخش‌های تم هماهنگی کامل ندارد:

- title و CTA آن از palette کهربایی استفاده می‌کند
- در حالی که مودال مجاور و برخی قسمت‌های فرآیند از palette چرمی/برند استفاده می‌کنند

### 10.2) آیا می‌توان اتوماسیون را در همین مودال اضافه کرد؟

از نظر فنی: بله  
از نظر UX و نگه‌داری: به‌صورت کامل، نه

پیشنهاد بهتر:

- داخل همین مودال فقط یک بخش سبک اضافه شود:
  - `اتوماسیون‌های این مرحله`
  - summary ruleها
  - دکمه‌ی `تنظیم اتوماسیون`
- با این دکمه یک drawer یا modal دوم باز شود
- builder کامل trigger / conditions / target / actions در آنجا قرار بگیرد

### 10.3) چرا builder کامل نباید داخل همین مودال فشرده شود؟

چون این مودال الان برای یک stage ساده است. اگر این موارد را هم واردش کنیم:

- trigger
- condition groups
- target selector
- time rule config
- action list

فرم خیلی سریع شلوغ، خطاپذیر و کند می‌شود.

### 10.4) پیشنهاد نهایی برای این مودال

فاز اول:

- مودال فعلی فقط برای stage metadata بماند
- رنگ‌ها با تم اصلی همسو شوند
- یک summary box برای automationها اضافه شود
- دکمه‌ی ورود به builder جدا داشته باشد

فاز دوم:

- از داخل همان stage، builder ruleها با context آماده باز شود
- یعنی stage / task_type / template از قبل prefill شده باشد

این روش هم سریع است، هم برای کاربر قابل فهم‌تر.

## 11) همسویی با workflow فعلی

## 13) تصمیم‌های اجرایی پیشنهادی

1. `Workflow` عمومی باقی بماند.
2. `Process Automation` به‌صورت موجودیت مستقل اضافه شود.
3. `process_templates` ساده‌تر شود و فیلدهای اضافی آن حذف یا deprecated شوند.
4. `template_stages_preview` فعلا حفظ شود.
5. مودال stage draft فقط summary automation داشته باشد، نه builder کامل inline.
6. builder جدا برای automation stage/process ساخته شود.
7. ruleها روی identifier پایدار ذخیره شوند، نه label فارسی.
8. time-based ruleها با scheduled jobs اجرا شوند، نه scan کور.

---

## 14) ریسک‌ها و هشدارها

- اگر process automation را داخل workflow فعلی هل بدهیم، سیستم به‌مرور غیرشفاف و brittle می‌شود.
- اگر ruleها روی label فارسی ذخیره شوند، تغییر نام optionها ruleها را می‌شکند.
- اگر first/last stage فقط از روی UI تشخیص داده شود، bugهای منطقی می‌گیریم.
- اگر time ruleها با scan دائمی اجرا شوند، هم پرمصرف می‌شوند هم دقت پایین می‌آید.
- اگر builder کامل را داخل مودال stage فشرده کنیم، UX ضعیف می‌شود.

## 15) نتیجه

بله، می‌شود اتوماسیون‌های موردنیاز کسب‌وکارها را روی همین ساختار پیاده کرد، اما نه با فشرده‌سازی همه‌چیز داخل workflow فعلی و نه با شلوغ کردن بیش از حد مودال stage draft.

راه درست و قابل توسعه این است:

- workflow عمومی را نگه داریم
- یک لایه‌ی process automation هم‌خانواده با آن اضافه کنیم
- از stage modal فقط به‌عنوان نقطه‌ی ورود و summary استفاده کنیم
- و builder کامل ruleها را جدا ولی هماهنگ با همان تجربه‌ی کاربری بسازیم
