# نقشه راه عملکرد، اهداف، پورسانت و فیش حقوقی HR

آخرین به‌روزرسانی: `2026-04-20`

## تصمیم‌های نهایی

- داشبورد منابع انسانی به مرکز محاسبه عملکرد، تحقق هدف، پورسانت و فیش حقوقی تبدیل می‌شود.
- تب‌های نهایی داشبورد:
  - عملکرد فعالیت‌ها
  - تردد
  - برنامه حضور
  - درخواست‌ها
  - تحقق اهداف
  - پورسانت‌ها
  - فیش حقوقی
- شرط‌ساز ضرایب فعالیت‌ها و پاداش‌ها باید از همان `WorkflowConditionsGroup` استفاده کند که در اتوماسیون استفاده می‌شود.
- فرمول‌های محاسباتی موجود (`calculation_formulas`) توسعه داده می‌شوند و سیستم موازی جدید ساخته نمی‌شود.
- seed پیش‌فرض فرمول‌ها فقط یک مورد است: `وزن * عدد ثابت`.
- سنوات hard-code قانونی ندارد؛ مبلغ/فرمول سنوات باید قابل تنظیم باشد و بر اساس تاریخ شروع همکاری محاسبه شود.
- هر آیتمی که وارد فیش حقوقی شد باید ledger status بگیرد تا در ماه بعد دوباره محاسبه نشود.

## فرمول عمومی

فرمول‌ها باید برای HR و بعدا برای workflow/actionها قابل استفاده باشند. ساختار فرمول کنترل‌شده است، نه SQL آزاد.

ورودی‌های مورد نیاز:

- فیلدهای رکورد اصلی، مثل `task.weight`
- فیلدهای کارمند، مثل `employee.hourly_rate`
- مقدار ثابت
- در ادامه، فیلدهای رکوردهای لینک‌شده در process و فیلدهای مرحله فرآیند

عملگرهای حداقلی:

- جمع، تفریق، ضرب، تقسیم
- `floor`, `ceil`, `round`, `min`, `max`
- شرط ساده `if`

## ضرایب فعالیت‌ها

ضرایب فعالیت‌ها باید از فیلدهای ثابت فعلی کارمند جدا شوند. فیلدهای فعلی مثل `early_bonus_rate` و `production_bonus_rate` فقط fallback و legacy هستند.

هر rule عملکرد فعالیت:

- روی یک یا چند نوع فعالیت (`task_type`) اعمال می‌شود.
- یک فرمول محاسباتی دارد.
- شرط‌های اعمال دارد.
- خروجی آن یکی از این نوع‌ها است: دستمزد، پاداش، جریمه، امتیاز.
- می‌تواند سازمانی یا override اختصاصی یک کارمند باشد.

## تحقق اهداف

برای هدف‌ها دو سطح ثبت لازم است:

- `goal_contributions`: سهم هر رکورد در تحقق هدف.
- `goal_milestone_events`: عبور از سطح‌های هدف مثل bronze/silver/gold/target.

پاداش هدف باید با همان فرمول عمومی قابل تعریف باشد و به جای ثبت قطعی مستقیم در فیش، به ledger فیش حقوقی وارد شود.

## پورسانت‌ها

مبنای محاسبه پورسانت:

- فاکتورهای تایید شده
- فاکتورهای تسویه شده
- فاکتورهای تسویه شده همراه با چک‌های وصول شده

اگر بخشی از فاکتور به خاطر چک در ماه جاری eligible نشد، بعد از وصول چک در ماه بعد فقط همان بخش جدید وارد پورسانت شود.

اولویت درصد/فرمول پورسانت:

1. rule اختصاصی پورسانت
2. درصد محصول
3. درصد پیش‌فرض کارمند
4. صفر

## فیش حقوقی

تب آخر باید `فیش حقوقی` نام داشته باشد و این منابع را جمع کند:

- دستمزد ساعتی
- دستمزد عملکردی
- پاداش دستی
- پاداش اهداف
- جریمه‌ها
- فاکتور فروش/هزینه‌های مرتبط با کارمند
- پورسانت
- سنوات
- بیمه و کسورات فعلی

ثبت فیش فقط باید entryهایی را مصرف کند که قبلا `included_in_payroll` نشده‌اند.

## وضعیت پیاده‌سازی فعلی

- فایل migration مرحله 113 ساختار `activity_performance_rules`، ledger فیش، contribution هدف، milestone هدف و پورسانت را اضافه می‌کند.
- Runtime فرمول در `utils/formulaRuntime.ts` پیاده‌سازی شده و از مسیرهای فیلدی مثل `task.weight` و `task.custom_score` پشتیبانی می‌کند.
- Runtime ضرایب فعالیت در `utils/activityPerformanceRuntime.ts` اضافه شده و همان شرط‌های workflow را روی فعالیت‌ها ارزیابی می‌کند.
- داشبورد HR رکورد کامل فعالیت را نگه می‌دارد تا فیلدهای اختصاصی wizard فرآیند در فرمول‌ها قابل استفاده باشند.
- هنگام ساخت فیش حقوقی، نتیجه ضرایب فعالیت‌ها به عنوان خط مستقل `ضرایب فعالیت‌ها` در فیش ثبت می‌شود.
- تب `تحقق اهداف` از snapshot واقعی goalها برای نیروهای انتخاب‌شده استفاده می‌کند و اهداف لمس‌شده را نشان می‌دهد.
- Runtime پورسانت در `utils/commissionRuntime.ts` اضافه شده و سه مبنا را محاسبه می‌کند: فاکتور تاییدشده، فاکتور تسویه‌شده، و تسویه به‌همراه چک وصول‌شده.
- تب `پورسانت‌ها` فعلا preview محاسبات را از روی فاکتورهای فروش، آیتم‌های محصول و درصد پیش‌فرض کارمند نمایش می‌دهد.
- تست‌های `formulaRuntime`، `activityPerformanceRuntime` و `payrollLedger` پاس شده‌اند و `tsc --noEmit` بدون خطا اجرا شده است.
