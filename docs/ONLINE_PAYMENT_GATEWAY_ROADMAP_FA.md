# برنامه درگاه پرداخت آنلاین و مدیریت حساب

## هدف

هدف این برنامه ساخت یک هسته پرداخت آنلاین برای تازه سیستم است که در فاز اول درگاه مرکزی تازه سیستم را برای پرداخت‌های متعلق به خود سامانه فعال کند و در فازهای بعدی، درگاه اختصاصی هر سازمان و دامنه اختصاصی را بدون بازنویسی معماری پشتیبانی کند.

## تفکیک محصولی پرداخت‌ها

پرداخت‌ها از ابتدا در سه دسته جدا نگه داشته می‌شوند:

- پرداخت‌های مرکزی تازه سیستم: تمدید اشتراک، شارژ هوش مصنوعی، شارژ پیامک و خرید کاربر اضافه.
- پرداخت فاکتورهای آنلاین سازمان خود تازه سیستم: فقط برای سازمانی که دسترسی SaaS Admin دارد و با درگاه مرکزی انجام می‌شود.
- پرداخت فاکتورهای آنلاین سازمان‌های مشتری: فقط وقتی فعال می‌شود که سازمان قابلیت دامنه اختصاصی و درگاه اختصاصی خودش را داشته باشد.

این تفکیک لازم است چون درگاه‌های پرداخت مثل زرین‌پال به پذیرنده، دامنه و فعالیت ثبت‌شده همان پذیرنده وابسته هستند و نباید پرداخت فاکتور tenantهای دیگر از درگاه مرکزی تازه سیستم عبور کند.

## قابلیت‌های پلن

ویژگی‌های زیر باید در مدیریت پلن‌ها قابل فعال یا غیرفعال باشند:

- `custom_domain`: اتصال دامنه اختصاصی سازمان
- `own_payment_gateway`: اتصال درگاه پرداخت اختصاصی سازمان
- `online_invoice_payment`: پرداخت آنلاین فاکتورهای عمومی
- `saas_account_billing`: مدیریت حساب و اشتراک
- `ai_credit_topup`: شارژ اعتبار هوش مصنوعی
- `sms_credit_topup`: شارژ اعتبار پیامک
- `extra_users_purchase`: خرید کاربر اضافه

سازمان دارای دسترسی SaaS Admin برای پرداخت‌های مرکزی و فاکتورهای خودش override دارد، اما این override نباید باعث فعال شدن پرداخت فاکتور tenantهای دیگر با درگاه مرکزی شود.

## تنظیمات اتصالات

در تب «تنظیمات > اتصالات» یک بخش «درگاه پرداخت آنلاین» اضافه می‌شود. در فاز اول این بخش برای تنظیم رفتار درگاه مرکزی زرین‌پال استفاده می‌شود:

- ارائه‌دهنده: زرین‌پال
- فعال/غیرفعال
- محیط آزمایشی یا واقعی
- دامنه پرداخت مرکزی، مانند `https://tazesystem.ir`
- مسیر callback، مانند `/payment/callback`
- واحد پول: ریال یا تومان
- عنوان نمایشی و توضیح پیش‌فرض پرداخت
- اعلام اینکه Merchant ID مرکزی باید در Secret سرور نگهداری شود
- امکان ثبت Merchant ID اختصاصی برای سازمان‌هایی که درگاه خودشان را دارند

برای فاز مرکزی، Merchant ID تازه سیستم از Secret سرور/Edge Function خوانده می‌شود و در تنظیمات عمومی نمایش داده نمی‌شود. برای درگاه اختصاصی tenant، Merchant ID همان سازمان در تنظیمات همان سازمان ذخیره می‌شود، اما RPC عمومی وضعیت پرداخت آن را برنمی‌گرداند و فقط Edge Function سمت سرور از آن برای درخواست/تأیید پرداخت استفاده می‌کند.

## دامنه اصلی و دامنه tenantها

دامنه اصلی تازه سیستم `tazesystem.ir` است و اینماد/درگاه مرکزی روی همین دامنه تعریف می‌شود. پنل هر tenant می‌تواند روی ساب‌دامین خودش اجرا شود، مثل:

```text
kalam.tazesystem.ir
```

در پرداخت‌های مرکزی، صفحه فاکتور یا حساب ممکن است روی ساب‌دامین tenant دیده شود، اما callback زرین‌پال باید روی دامنه مرکزی ثبت‌شده باشد:

```text
https://tazesystem.ir/payment/callback
```

بعد از تأیید پرداخت، سیستم کاربر را به origin اولیه همان tenant برمی‌گرداند. بنابراین در تنظیمات، «دامنه درگاه» به معنی دامنه callback و ترمینال پرداخت است، نه لزوماً دامنه‌ای که صفحه فاکتور از آن باز شده است.

برای درگاه اختصاصی tenantها در فاز آینده، callback باید مطابق دامنه ثبت‌شده همان پذیرنده باشد.

## صفحه فاکتور آنلاین

در صفحه عمومی فاکتور فروش، دکمه پرداخت آنلاین فقط وقتی نمایش داده می‌شود که:

- فاکتور فروش باشد؛
- مانده قابل پرداخت مثبت باشد؛
- سازمان مالک فاکتور مجاز به پرداخت آنلاین باشد؛
- تنظیمات درگاه برای همان سازمان فعال باشد.

برای سازمان SaaS Admin، فوتر چسبنده پایین صفحه نمایش داده می‌شود:

```text
مبلغ قابل پرداخت: ...        پرداخت سریع
```

تصمیم نمایش این فوتر باید از سمت دیتابیس/سرور برگردد، چون صفحه عمومی فاکتور anonymous است و نباید فقط به تصمیم سمت کلاینت اعتماد کند.

## ثبت دریافت فاکتور

پرداخت موفق فاکتور باید علاوه بر جدول تراکنش‌ها، در جدول دریافت‌های همان فاکتور نیز ثبت شود تا مانده فاکتور، چاپ‌ها، گزارش‌ها و محاسبات مالی با وضعیت واقعی هماهنگ بمانند.

ردیف دریافت آنلاین باید این ویژگی‌ها را داشته باشد:

- `payment_type = online`
- `status = received`
- مبلغ برابر مبلغ verified شده
- تاریخ ثبت برابر زمان تأیید تراکنش
- متادیتای منبع شامل شناسه تراکنش، Authority و Ref ID
- قفل‌شده و غیرقابل ویرایش/حذف از UI

در صورت نیاز به اصلاح، مسیر درست عملیات برگشت/ابطال یا ثبت اصلاحیه است، نه ویرایش دستی ردیف دریافتی که از درگاه آمده است.

## هسته تراکنش

همه پرداخت‌ها در جدول مرکزی تراکنش ثبت می‌شوند. این جدول برای همه use caseها مشترک است:

- `gateway_scope`: `system` یا `org`
- `provider`: مثل `zarinpal`
- `purpose`: مثل `online_invoice`, `saas_renewal`, `ai_topup`, `sms_topup`, `extra_user`
- `org_id`
- `module_id`
- `record_id`
- `amount`
- `currency`
- `authority`
- `ref_id`
- `status`
- `metadata`

Verify باید idempotent باشد. اگر تراکنش قبلاً تأیید شده باشد، ثبت دوباره نباید دریافت تکراری روی فاکتور ایجاد کند.

## فازهای اجرا

1. افزودن featureهای پلن و مستند برنامه.
2. افزودن تنظیمات درگاه آنلاین در اتصالات.
3. افزودن جدول تراکنش و RPC وضعیت پرداخت عمومی فاکتور.
4. افزودن Edge Function پرداخت زرین‌پال برای ایجاد و تأیید تراکنش.
5. افزودن فوتر چسبنده پرداخت سریع در فاکتور آنلاین فروش برای سازمان SaaS Admin.
6. ساخت تب «مدیریت حساب» در تنظیمات برای پلن، تمدید، کاربر اضافه، شارژ هوش مصنوعی و شارژ پیامک.
7. افزودن دامنه اختصاصی و درگاه اختصاصی برای tenantها.

## نکات عملیاتی

- بررسی drift دیتابیس production باید دستی انجام شود.
- دامنه callback باید با دامنه ثبت‌شده ترمینال زرین‌پال تطابق داشته باشد.
- برای هر تغییر آینده در مسیر پرداخت یا فعال‌سازی دامنه اختصاصی، دامنه در تنظیمات نگهداری می‌شود و در کد hardcode نمی‌شود.
