# عیب‌یابی و بازیابی

ابتدا کد نصب، زمان رخداد، مرحله و کد خطا را یادداشت کنید. رمز، token، hash رمز، فایل محیطی و محتوای دیتابیس را به تیکت ضمیمه نکنید. دستورهای زیر روی سرور مقصد اجرا می‌شوند:

```bash
sudo python3 /opt/kalamapp/release/installer/local/cli.py status
sudo python3 /opt/kalamapp/release/installer/local/cli.py doctor
sudo python3 /opt/kalamapp/release/installer/local/cli.py logs
```

فایل `/opt/kalamapp/diagnostics.json` فقط اطلاعات محدود سلامت را دارد. پس از بررسی، آن را با اقدام خودتان در زبانهٔ سلامت پروندهٔ مرکزی وارد کنید. تیکت موجود مشتری را با کد آن به پرونده پیوند دهید. دریافت گزارش یا ساخت تیکت خودکار انجام نمی‌شود.

| کد یا وضعیت | اقدام |
|---|---|
| `VERIFY_FAILED`، `CHECKSUM_MISMATCH` | فایل را از همان انتشار دوباره دریافت کنید و کلید عمومی مستقل را بررسی کنید. فایل ناقص یا دست‌کاری‌شده اجرا نمی‌شود. |
| `RELEASE_NOT_ACCEPTED`، نبود بستهٔ جاری | آزمون انتشار تکمیل نشده است؛ تغییر دستی نتیجهٔ پذیرش مجاز نیست. این خطا با نصب npm یا pull روی مشتری حل نمی‌شود. |
| `UNSUPPORTED_OS`، `LOW_MEMORY` | سیستم‌عامل/معماری و منابع مقصد را با نیاز همان انتشار تطبیق دهید. |
| `LOW_DISK` | فضای مقصد و Docker را بررسی کنید؛ فایل داده یا backup را بدون بررسی حذف نکنید. |
| `PORT_IN_USE` | سرویس اشغال‌کنندهٔ ۸۰/۴۴۳ را مشخص کنید؛ نصاب آن را خودکار متوقف نمی‌کند. |
| `TLS_KEY_MISMATCH`، `ENDPOINT_FAILED` | تطابق نام/IP، تاریخ اعتبار، زنجیرهٔ گواهی، اعتماد CA و DNS محلی را بررسی کنید. |
| `UNHEALTHY_SERVICE` | سلامت container مربوط را روی همان سرور بررسی کنید؛ لاگ خام ممکن است اطلاعات مشتری داشته باشد. |
| `SQL_REVIEW_REQUIRED` | اجرای SQL قبلی قطع شده است. وضعیت واقعی دیتابیس و checksum همان فایل باید بررسی شود؛ حذف `sql_in_flight` یا اجرای کور migration ممنوع است. |
| `SQL_HISTORY_MISMATCH` | فایل قبلاً اعمال‌شده تغییر کرده است؛ همان بستهٔ معتبر را بازیابی کنید و فایل SQL قدیمی را ویرایش نکنید. |
| `WORKER_INTERRUPTED` / نیازمند بررسی | ابتدا process قبلی، فایل‌های خروجی و قفل منبع بررسی شوند. ثبت بررسی در پنل، قفل انتقال را باز یا عملیات را دوباره اجرا نمی‌کند. |
| `UNCLASSIFIED_TABLES`، `SCHEMA_DRIFT` | schema با فهرست انتقال تأییدشده منطبق نیست؛ پیش از خروجی نهایی، طبقه‌بندی و آزمون جداسازی باید تکرار شود. |
| `MFA_REQUIRES_REVIEW` | MFA را حذف یا خاموش نکنید؛ انتقال به مسیر سازگار و آزموده‌شده نیاز دارد. |
| `TRANSFER_DECRYPT_FAILED` | کلید خصوصی همان مشتری، رمز کلید و checksum فایل را بررسی کنید؛ plaintext تأییدنشده نگهداری نمی‌شود. |
| `REPORT_NOT_SENT` | قطع ارتباط مرکز، نصب محلی را متوقف نمی‌کند؛ گزارش دستی قابل استفاده است. |

## قطع SSH، reboot و ادامه

کار صف‌شدهٔ مرکزی به مرورگر وابسته نیست. قطع ترمینالِ نصب ممکن است اجرای مقصد را قطع کند. پس از اتصال، ابتدا `status` و `doctor` را اجرا کنید و همان بسته و پرونده را مجدداً به نصاب بدهید. قفل هم‌زمانی اجازهٔ دو عملیات روی یک مسیر نصب را نمی‌دهد. برای ادامه، پوشهٔ `private` یا `state.json` را حذف نکنید؛ این کار می‌تواند کلیدهای رمزگذاری و امکان بازیابی را از بین ببرد. اجرای SQL نامطمئن به بررسی دستی می‌رسد.

## بازیابی backup

قبل از هر کار، نسخهٔ نرم‌افزار و کد نصب backup را تطبیق دهید. checksum باید از سابقهٔ جداگانهٔ بازیابی آمده باشد. این فرمان دادهٔ مقصد را جایگزین می‌کند و تأیید کد نصب می‌خواهد:

```bash
sudo python3 /opt/kalamapp/release/installer/local/cli.py restore --file ./backup.enc --recovery-key ./recovery.key --backup-checksum REPLACE_WITH_TRUSTED_SHA256
```

ابزار ابتدا رمزگشایی، بررسی فایل‌ها و بازیابی آزمایشی دیتابیس جداگانه را انجام می‌دهد. سپس دیتابیس اصلی و درخت فایل را جایگزین می‌کند و نسخهٔ قبلی فایل‌ها را برای بررسی نگه می‌دارد. آزمون واقعی این مسیر روی همان انتشار، شرط تحویل است؛ آزمون واحد جای آن را نمی‌گیرد.

اگر migration ارتقا شکست خورد، نسخه و backup پیش از ارتقا را نگهدارید. دیتابیس ارتقایافته را با فایل برنامهٔ قدیمی راه‌اندازی نکنید. ابتدا محیط بازیابی با نسخهٔ متناظر backup آماده شود، restore واقعی انجام و ورود، روابط، فایل‌ها و اتصال‌ها بررسی شوند.

## شکست انتقال نهایی

اطلاعات منبع حذف نمی‌شود و قفل آن پس از شکست خودکار باز نمی‌شود. ابتدا تمام عملیات و خروجی‌های مقصد را متوقف کنید. بازفعال‌کردن منبع فقط با اثبات توقف مقصد و بررسی جداگانهٔ اپراتور مجاز است؛ ابزار خودکار بازگشت ابر و همگام‌سازی دوطرفه فعلاً ارائه نشده است. وجود قفل تنها روی جدول‌های مستقیم دارای `org_id`، برای تأیید انتقال نهایی کافی نیست؛ فایل‌ها، جدول‌های وابسته و کارهای خروجی نیز باید آزموده شده باشند.
